# 长缨辅学 V1 范围与数据衔接

## 产品范围

V1 只处理小学阶段的培训机构教学、学校教学、学生学习动态、家长学生关联、
升年级与升学衔接，以及历史教学查询。

当前工作台围绕“当前教学周期”组织。培训机构模式在正常学期显示晚托和周末课，
在寒暑假显示对应假期班；结束的周期进入往期教学。学校模式保留独立入口布局，
但当前只按账号真实可见的班级、学生和既有教学事实组织；学校、学年、学期、课节
与时间段等标准化学校数据结构尚未全部落表，不由界面虚构。

## 复用的现有能力

- 登录、密码更新和会话校验；
- 学生独立账号与家长学生多对多关系；
- 教师、学生、家长和管理员的既有权限；
- 班级、调班、毕业归档和班级历史；
- 题库、组卷、作业、提交、成绩、错题与教学跟进；
- 教师可见的学生成长档案和时间线；
- 教师已有的待办、到期提醒、家长回访与班级工作台；
- 原系统 `/classic` 继续作为完整维护入口。

## V1 新入口

- `/v1`：登录和身份识别；
- `/v1/workspace`：培训机构或学校工作台；
- `/v1/student`：学生列表与学生动态；
- `/v1/history`：往期教学查询入口；
- `/v1/transition`：升年级与升学衔接入口。

V1 工作台中的晚托、周末课、班级、作业与错题、学习进度、待办等日常卡片已经
改为在 V1 登录态内直接读取现有受保护 API，不再把普通教学查看动作跳回
`/classic`。原系统继续保留给明确的维护入口和暂未原生化的管理动作。V1 不复制
一套平行数据，也不绕过原权限。

学校模式中的“今日课表”在真正的学校课表模型落表前，不生成上课时间、教室或
学科安排。当前面板只显示可核对的可见班级、学生关系和教师待办，并明确标注这是
“今日教学事实概览”而不是标准化课表。

移动端为现有班级、学生和成长档案读取增加短缓存、并行请求和空闲预热；学生连续
档案入口也并行读取多个教学归属，减少逐班串行等待。以上优化只改变读取方式，
不新增写入路径。日常详情面板和往期教学摘要不再静默只取前 8/10/12 条记录；
当前账号可见的班级与学生会按小批次并发读取，在保留完整可见范围的同时避免一次
性发出过多请求。首页预览仍可保持紧凑，但完整入口不再因演示阶段的数量上限漏人。
基础 V1 的教师学生集合也不再只检查前 30 个班级：它会按 8 个班级一批读取全部
当前可见教学归属，因此首页“当前学生”计数、学生列表和详情面板使用同一可见范围。

## 连续学生档案

学生继续使用现有 `users.id` 作为稳定键。换班和毕业归档通过
`student_class_history.student_id` 关联，不创建新的学生记录。V1 页面复用
`/teacher/students/{id}/growth-profile`，把当前教学归属、作业、成绩、薄弱知识、
跟进、家长关联和时间线汇总到同一学生页面。

学生详情页对已经由受保护成长档案接口返回的数据不再静默只展示前几条：教学建议、
作业、薄弱知识和历史时间线会完整呈现当前接口已经返回的可见记录；首页仍只保留紧凑
预览。此调整不增加新的 API 请求，也不改变任何写入或权限行为。

同一稳定学生 ID 的多个教学项目会聚合显示；已归档的重复测试账号不会继续进入
活动学生列表。系统不会仅凭同名自动合并真实学生。

学生页的“不会 → 学习中 → 基本掌握 → 稳定掌握”仍只作为展示语义，不写成
自动能力结论。V2 已把学习证据统一为四个事实维度：作业/测验自动形成 performance，
教师以追加式 `learning_evidence_events` 记录 independent、retention、transfer；撤回
保留原事件并从当前有效证据中排除。四维证据可以进入同一连续档案、阶段对比与成长报告，
但系统仍不依据一次成绩、平均分或“维度齐全”自动判定掌握、稳定掌握、能力高低或分层。

`changying.domain.student_continuity` 预留了教学模式、教学周期、掌握阶段、
提交人、数据域、多身份和衔接计划的稳定词汇。它暂时不修改生产表。

## 历史与衔接

往期教学页面已直接读取当前账号全部可见学生的真实班级历史与成长时间线，提供连续
档案摘要，并支持按学生和真实教学归属筛选；读取使用小批次并发，不再依赖页面上前
几名学生的 DOM 占位。当前数据库尚未标准化的学年、学期字段不会由界面虚构。

升年级与升学衔接页会读取学生当前年级、班级历史、阶段成绩、薄弱知识和下一步
教学建议，形成只读“当前档案事实”，并把八个衔接步骤区分为“已有事实可读取”
和“仍需教师判断/后续落表”。它不会自动改变学生年级、学校或教学归属；真正改变
档案关系时仍沿用现有受权限保护的操作。

## 权限边界

V1 只调用现有受保护接口，后端继续执行角色和学校范围校验。学校域、机构域、
家庭关系和授权共享域已经进入领域契约，但真正的跨域共享授权尚未开放。

## 仍需后续落表的能力

- 同一真实用户的多身份目前是界面选择和领域契约，底层账户仍是单角色；
- 学年、学期、教学周期和学校组织层级尚未全部落成独立数据表；
- 掌握阶段仍不作为数据库自动结论字段；四维学习证据已经标准化，其中教师观察采用追加式事件落表，但掌握、稳定掌握、能力诊断与分层仍保留为教师判断；
- 衔接计划目前能读取真实档案事实并展示八步准备度，但步骤尚未保存为独立计划记录，也未启用自动分析；
- 学校教学的“今日课表”目前只做真实教学事实概览；备课、测验和教学评价继续复用现有能力，尚未形成独立学校数据域和标准化课表模型；
- 往期教学已连接真实班级历史、时间线和教学归属筛选，但尚未提供标准化学年/学期筛选 API；
- 作业完成主体尚未写入现有提交表，领域枚举已预留四种状态。

这些未落表能力必须继续明确标注，不使用虚构的真实学生、学校、课表或成绩。


## 2026-09-22 整体完整性审查

本轮按“产品边界 → 核心教学闭环 → 连续学生档案 → 权限与生产安全 → 历史/衔接 → 架构债务”重新核对 main 与生产基线。结论不是“全部完成”，而是把已完成能力与真实剩余缺口分开管理。

### 已形成可用闭环

- 教师可按年级、科目、教材和模块组织综合/专项练习，学生在线作答，客观题与受控主观题结果进入既有作业/测验记录。
- AI 针对性练习可以引用已有 assessment context；教师审核后再布置，不绕过教师确认。
- 互动课堂已经覆盖课堂环节、quick check、补讲决策、学生讲解、教师明确加分与课堂复盘讲义。
- 课堂讲义采用不可变版本发布：旧版保留、当前版唯一、学生只看当前有效发布；教师可查看相邻版本差异与冻结来源元数据。
- “本堂课完整课堂记录”把练习、互动、检测、教师决策、明确加分和讲义版本组织在同一课堂事实视图中。
- 标准化 learning evidence 已进入同一学生连续档案；教师/管理员可查看 source type/source id 追溯来源，学生/家长共享视图继续隐藏内部技术标识。
- 系统保持 `masteryInferred=false` 的边界：学习事实、积分和单次成绩不自动升级为“已掌握/稳定掌握”等长期判断。

### P0：当前不应再补的风险项

以下项目虽然仍是架构债务，但在现阶段不应为了“完整”直接改生产表或大规模重构：

- legacy ORM/Session、认证依赖和大型内嵌前端的整体迁移；
- 多身份底层账户模型；
- 学校组织、学年/学期/标准课表的一次性建模；
- 自动掌握度、能力诊断和自动分层。

这些都必须继续遵守小批次迁移、隔离测试、明确授权和生产回滚边界。

### P1：产品完整性的真实剩余缺口

1. **升年级/升学衔接计划尚未落表。** 当前能读取同一 student_id 的真实档案事实并展示八步结构，但计划步骤、教师判断、执行状态和复查结果还不能形成持久历史。
2. **标准化教学周期不足。** 题库已有 semester、教学方案已有 academic_year/term，但学生历史与 V1 查询仍没有统一的 school year / term / winter / summer cycle 实体，因此跨学期查询主要依赖现有时间线和班级历史。
3. **作业完成主体未落表。** `CompletionActor` 已有领域词汇，但提交记录仍不能区分 student / parent_assisted / parent_submitted / teacher_recorded。
4. **多身份仍是 UI/领域契约。** 同一真实账户不能在数据库层拥有多个可授权身份；当前不影响单角色生产使用，但限制学校/机构双重任职等场景。
5. **学校课表仍是事实概览。** 尚无标准课节、教室、课程表实体；不应由 UI 虚构。
6. **历史查询缺少标准化学年/学期筛选 API。** 当前真实班级历史与连续档案可查，但筛选维度仍不完整。

### P2：架构完整性缺口

- C2 服务层仍在进行中，数据库型业务仍有较多逻辑位于 legacy；
- API Router、数据库层与前端资源拆分仍应按 ARCHITECTURE 的 D/E/F 阶段渐进执行；
- README 的代码结构描述落后于当前已新增的 learning evidence、classroom review、handout release 等模块，应在功能稳定后同步更新，而不是用文档驱动生产重构。

### 后续处理顺序

后续不再零散加页面，按以下顺序处理：

1. 先把**衔接计划**做成“教师明确保存、追加历史、可撤回/关闭、只读回看”的独立记录，继续绑定稳定 student_id；不自动改年级/班级。
2. 再建立**教学周期只读统一模型**，先映射现有 academic_year/term/semester/班级历史，不立即重写生产表。
3. 再补**完成主体**，要求兼容旧 submission 数据并默认“不推断”；只有新提交明确记录。
4. 最后评估多身份和学校标准课表是否已经有真实业务数据支撑，再决定是否落表。

每一步必须继续满足：独立分支 → PR → exact-head CI/Harness Guard → 合并 → Render 自动部署 → 生产只读验收；不得把“补齐结构”解释为自动修改学生掌握状态或覆盖历史数据。


### 2026-09-22 P1 收口状态与决策门

按上述固定顺序，前三项已经形成可验证实现：

- 衔接计划：#322 已提供教师明确保存、追加历史、关闭与只读回看；仍绑定稳定 student_id，不自动改年级/班级。
- 教学周期：#323 已提供 storage-neutral 的只读统一模型，只映射现有 TeachingProgram academic_year/term/semester，不制造新的生产周期事实。
- 完成主体：#324/#325/#327 已为新 Submission 增加 nullable completion_actor；历史记录保持 NULL=未知，不回填、不反推。新学生提交明确写 student，并可进入新证据 context。

剩余 P1 不应直接落表，先设事实门槛：

1. **多身份账户暂缓落表。** 当前 User 仍是单 role 授权模型；尚无生产事实证明同一账号必须同时拥有 teacher/admin/parent 等多个授权身份。若未来出现真实双重任职，再以“账户主体 + 角色授予”小批次迁移；在此之前不把 UI 身份切换包装成数据库多身份。
2. **标准课表暂缓落表。** 当前已有班级、教师、作业、课堂 session 等事实，但没有稳定的标准课节、教室、周期性课表来源。没有真实排课数据前，不创建虚构 timetable/room/period 记录。
3. **学年/学期历史筛选继续保持保守。** #323 已统一可确认的 TeachingProgram 周期事实，但历史 Assignment/Classroom 并未持久关联 TeachingProgram/cycle。不得仅凭日期猜测某条历史教学事实属于哪个学年/学期。后续只有在新教学事实能够明确携带 cycle source/id 后，才新增精确 cycle 筛选；旧数据继续按时间线、班级历史、科目和教师所有权查询。

因此，当前 P1 的正确收口不是继续新增三个推断性表，而是保留明确 provenance 缺口，等待真实业务事实后再迁移。下一阶段转入 P2 渐进架构整理，不改变既有教学语义。
