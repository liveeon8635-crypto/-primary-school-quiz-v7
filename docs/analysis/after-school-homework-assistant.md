## 0. 结论摘要（先看这里）

1. **复用度高**：班级码/座位登录、讲课屏、`_ai_call`、错题本、`AIUsageLog` 都可直接复用；缺口是「学生侧调用大模型」「作业通知结构化」「求助队列」三块。
2. **一个关键发现（影响模型选型）**：`app_v924.py:3104-3108` 把 `deepseek-v4-flash` 和 `deepseek-v4-flash-vision-exp` 都**强制映射**成 `deepseek-flash`（仅当 base_url 为 DeepSeek 官方时，`_ai_effective_model` @3165-3169）。也就是说，**按现有配置界面填 `deepseek-v4-flash-vision-exp` 实际发出的是 `deepseek-flash`**，视觉实验模型无法被测试到。要评估它，需要改这张映射表（或给视觉模块独立配置），见 §3.4。
3. **`_ai_call` 不能直接给学生用**：它是同步 `requests.post`、按「学校」维度限流（60 次/小时，`app_v924.py:3109,3250-3254`）、`AIUsageLog.user_id` 记真实用户、且所有调用方都在教师/管理员侧。学生侧要新增**按学生限流 + 按班级并发闸**，否则一个班同时求助会耗光全校额度。
4. **晚托机构 = 长缨里的一个 School（租户）**；作业通知上的「学校+班级」是**通知里的文字标签**，与长缨 `classes` 表不是一回事，设计上用「分组标签」承载，再映射到长缨班级/学生。
5. **建议 MVP**：仅一至六年级数学；教师粘贴文字为主（截图为次）；学生拍题 → 识别 → 确认 → 单一解法；无法确定就升级给老师。全部学生侧功能挂**默认关闭**的功能开关。
6. **隐私底线**：发给模型的只有「题目文字」和「作业通知文字」，**不含姓名、用户名、学生 ID、班级名、机构名**；照片识别后立即删除，不入库。

7. **登录主路径改为「设备绑定」**（家长自带平板，绑定后保持登录）；日码+座号降为机构备用平板的备用方式（§12）。
8. **新增「参加/未参加」状态**：看板、清单分配、AI 求助入口、设备绑定只面向已参加学生；未记录纸质同意书的学生**不能**设为参加（代码硬性前置）。试点效果用**参加学生自身前后对比**（前 2 周仅清单、之后开 AI），**不采集未参加学生的数据**，且为无对照的描述性对比（§14）。
9. **限流必须重估**：现有「每校每小时 60 次、含全部功能」的额度（`app_v924.py:3109,3250-3254`）撑不住晚托高峰，且会和教师侧 AI 互相挤占，需独立额度桶（§3.5b）。

## 2. 作业清单导入（教师侧）

### 2.1 流程

1. 家长把学校的当日作业通知（文字或截图）转给晚托教师。
2. 教师在长缨「晚托」页粘贴文字，或上传截图（**MVP 建议文字优先**，截图为第二步，原因见 §8/§11：截图 OCR 精度未知）。
3. 系统调用**文本模型**（截图则先走视觉识别得到文字，再走文本解析；两次调用解耦）把通知解析成结构化清单：学科、内容、页码、要求；并尽力识别「学校 + 班级」。
4. 教师在确认页逐条修改/删除/补充，选择要布置的学生（可多选、按分组批量），点击**发布**。
5. 发布后生成「今日作业清单」，学生端可见并可逐项勾选完成。

教师确认是**硬门槛**：AI 解析结果在教师点「发布」前，学生不可见。

### 2.2 分组：双维度（用户决定 2）

- **晚托班**（机构内的实际上课单位）：用于**登录**（日码、座号）和**教师看板**。
- **「学校+班级」标签**（如「实验小学 三(2)班」）：只用于**分配作业**。一个晚托班可含多个标签；一个学生有且仅有一个标签（若同一学生需要两个标签，如转学过渡，【未确认】，MVP 先不支持）。
- 导入通知时，AI 从通知文字里抽取候选标签，教师确认；系统按「标签 → 学生」自动勾选收件人，教师可手动增减。
- 与存量的关系：长缨 `classes`（`app_v924.py:73`）= 晚托班；标签为独立维度，存于新表 `student_group_tags`（§2.3），**不改 `classes`、`class_students`**。
- 【未确认】晚托班是否对应现有 `classes` 的一行：设计取"是"。若机构想让一个晚托班跨多个现有 `classes`，需再议。

### 2.3 数据结构草案（均为**新增表 → 触发 §6 schema/迁移高风险**，且命中 V1 冻结规则「新增第一层业务概念/生产表需走 V1.1/V2 评审」，故需用户先批）

```
homework_notices            -- 一次导入（一条通知）
  id, school_id, created_by(user), group_label, source_kind(text|image),
  raw_text            -- 教师粘贴文字或识别后的文字（可含他人信息，见 §7，发布后可清空）
  parse_status(pending|parsed|failed), parse_model, created_at, published_at, status(draft|published|archived)

homework_items              -- 清单中的一条
  id, notice_id, school_id, seq, subject, content, page_ref, requirement, due_date, deleted(bool)

homework_item_recipients    -- 布置给谁 + 完成状态
  item_id, student_id, school_id, done_at(nullable), done_by(student|teacher)
  -- 唯一约束 (item_id, student_id)

student_group_tags          -- 学生所属「学校+班级」标签
  school_id, student_id, group_label   -- 唯一约束 (school_id, student_id, group_label)

help_requests               -- 求助（§3、§5）
  id, school_id, student_id, item_id(nullable), state(...), question_text(学生确认后的文字),
  topic(知识点标签), ai_status, verify_status, escalated_at, resolved_at, created_at

  id, request_id, role(student|ai|teacher), content, created_at, purge_after
```

- 不新增图片列；`help_requests` 不存原图（§3.6）。
- 全部表带 `school_id`，所有查询强制 `school_id == u.school_id`（沿用现有租户隔离做法）。
- 表注册方式：【未确认】项目里既有 ORM `Base`（`app_v924.py`）与 SQLAlchemy `Table` 动态注册（`v1_classroom_execution.py` 等）两种做法，需看 `docs/adr/` 与迁移规则后再选，因迁移文件受限，**本设计不写迁移**。

> v2 补充：另有 `club_participation`（+events）、`student_devices`、`device_bind_tokens`、`after_school_day_sessions`、`teacher_interventions`、去标识聚合表，见 §12、§14；全部新表合并为**单独的迁移 PR**（§10.2 的 M1）。

### 2.4 API 草案（均需 `need(u,"teacher")` 或 `need(u,"student")`）

教师侧：
- `POST /teacher/homework/notices/parse`  body `{groupLabel?, text}` → 返回结构化草稿（仅返回，不入学生可见态）
- `POST /teacher/homework/notices/parse-image` （第二期）multipart 图片 → 识别文字 → 同上；服务端处理完立即丢弃图片
- `PUT /teacher/homework/notices/{id}` 编辑条目/分组/收件人
- `POST /teacher/homework/notices/{id}/publish` 发布（幂等）
- `GET /teacher/homework/today` 当日各学生清单完成情况
- `GET/PUT /teacher/students/group-tags` 学生分组标签批量维护

学生侧（挂功能开关，默认关）：
- `GET /student/homework/today` 今日清单
- `POST /student/homework/items/{id}/done` 勾选完成

解析提示词要求模型**仅输出 JSON**（用 `_ai_json` :3234 解析），失败即返回「解析失败，请手动录入」，不自动重试多次（控成本）。

## 3. 拍照求助流程（学生侧）

### 3.1 步骤

```
学生点「这道题我不会」
 → 取景提示（只拍题目区域，别拍到人脸/姓名/整页）
 → 拍照上传（单张，限大小/像素）
 → [调用 A：视觉识别] 图片 → 题目文字（+置信度/是否含图形）
 → 服务端立即删除照片（内存中处理，不落盘不入库）
 → 学生看到识别文字，可修改后点「确认」      ← 硬门槛
 → [调用 B：文本讲解] 仅发送确认后的题目文字 → 单一解法、分步展开
 → 展示 + 固定提示「AI 可能出错，请自己判断」
 → 学生可点「我看不懂 / 我觉得不对」→ 升级给教师（§5）
```

### 3.2 取景提示（前端文案草案）
「只拍这一道题，让题目占满画面；避开人脸、姓名、手写的班级学号。光线要亮，别有阴影。」上传前显示裁剪框；不提供整页多题（见 §8，整页多题放测试观察项而非 MVP 承诺）。

### 3.3 两次独立调用
- **A 识别**：入参=图片；出参 JSON `{text, hasFigure, confidence, notes}`。不带任何学生信息，不带讲解任务。
- **B 讲解**：入参=学生确认后的文字（+年级，**不是**学生身份；年级可用于控制讲法深浅，属弱识别信息，见 §7）；出参 JSON `{method, steps:[{n, text}], answer, knowledgePoint, caveat}`。**只给一种解法**（提示词硬性要求），按步骤展开；学生可逐步点开（减少一次看完直接抄答案）。
- 两次调用互不依赖：识别用错模型/失败，不影响文本讲解用的稳定模型；视觉模块可单独切换（§3.4）。

### 3.4 视觉模块可切换（接口抽象）

```
  实现：DeepSeekVision / QwenVision / ZhipuVision（按配置选择）
```
- 配置项：视觉 provider/base_url/model/key 与文本模型**分开存**（沿用 `SchoolAIConfig` 的思路，但不应把两套塞进同一行；新增字段 = schema 变更，或用单独配置表）。【未确认：用新增表还是环境变量。倾向环境变量承载平台级默认 + 学校级覆盖，环境变量属 §6，需用户操作。】
- **首选评估对象 `deepseek-v4-flash-vision-exp`**：
  - 现状阻碍：`app_v924.py:3104-3108` 会把该名映射为 `deepseek-flash`（官方 base 时），实际并未调用到视觉实验模型 → 需要让视觉模块**绕过**该别名表（独立 `_vision_effective_model`，不改文本侧行为）。

- 切换方式：运维/管理员改配置即可，无需改代码；评估期可对同一批图并行跑多家做 A/B（§8）。

### 3.5 同步调用的风险
`_ai_call` 同步阻塞线程，默认 `timeout=90`。晚托场景 N 个学生同时拍照，会占满 Web worker。当前是单实例、`0.5c-512mb`（Issue #174，2026-09-29 内容；与 `render.yaml` 的 free 描述不一致，【未确认】以 Render 控制台为准）。设计要求：
- 学生侧调用超时缩短（识别 ≤20s、讲解 ≤30s），超时即提示「稍后再试/找老师」；
- 单学生同一时刻 1 个在途请求；单班/全校并发上限（例如全校 ≤4 并发，超出排队提示）；
- 评估是否改为「提交任务 + 前端轮询结果」模式（沿用轮询范式）而非长连接，避免占住请求线程。

### 3.5b 限流与容量（用户决定 9）

现状：`_ai_rate_check`（:3250）按**学校**统计最近 1 小时 `AIUsageLog` 全部功能的条数，默认上限 60（`AI_HOURLY_LIMIT`，:3109，环境变量可调，范围 5–1000）。

晚托高峰估算（假设，【未确认】需现场数据）：30 人 × 3–5 次求助 = 90–150 次求助/晚；每次 2–3 次模型调用（识别+讲解+偶发复核）= **约 180–450 次调用/晚**；若集中在 1 小时内，等于 180–450 次/小时，**是现有 60 次/小时的 3–7 倍**。直接把 `AI_HOURLY_LIMIT` 调大会让学生流量挤占（或被挤占）教师导入通知、批改辅助等功能。

设计：
| 层级 | 草案值（均可环境变量调整，需压测校准） | 目的 |
|---|---|---|
| 每生每分钟 | ≤ 2 次求助 | 防连点 |
| 每生每晚 | ≤ 8 次求助 / ≤ 24 次调用 | 防刷、控成本 |
| 学校级·学生求助桶（新，独立计数，按 `feature` 前缀 `homework_help_*` 统计） | ≈ 300 次调用/小时（= 约 30 人高峰上限 450 的 2/3 与均值之间，待压测） | 容纳高峰又不无限 |
| 学校级·教师侧桶（保持现状 60） | 不变 | 教师功能不被学生挤占 |
| 同时在途的学生 AI 请求（全校） | ≤ 8，超出排队/提示"稍等几秒" | 同步线程占用，见 §3.5 |
| 超限表现 | 429 + 友好文案 + 自动"请老师帮忙"入口，不静默失败 | 体验 |

- 实现方式：新增独立的计数函数（按 `feature` 分桶），**不改 `_ai_rate_check` 既有语义**。
- 压测：P4 合入前用 30 个并发模拟学生跑一遍（桩模型），记录 P95 延迟与线程占用；单实例 `0.5c-512mb`（Issue #174，【未确认】以 Render 控制台为准）。

### 3.6 照片不存档
- 路由内仅在内存持有图片字节；`HTTPException`/异常路径同样不落盘；日志不得打印 base64/文件名。
- **不得复用 `HomeworkMedia`**（它存原图 :188-200）。
- `AIUsageLog` 只记字符数/token/耗时（:461 现有字段正合适），**不记 prompt 原文**（现状本来就只记长度，**已核实** `_ai_call` finally 块 :3256 起）。
- 反向风险：异常时容易把图片带进 traceback → 需有测试断言「出错日志不含图片内容」。

## 4. 数学程序化校验（与 AI 解答交叉）

目的：模型数学出错是已知风险，对**可机器验算**的小学题，不让「AI 自己说对」成为唯一依据。

### 4.1 依赖（用户决定 7：同意新增 sympy）

`requirements.txt` 目前没有 sympy（已核实）。同意新增，约束：
- 固定版本号（沿用该文件的 pin 风格），单独 PR 引入并附体积/冷启动影响说明；
- 禁止对模型给出的表达式直接 `sympify`/`eval`（有代码执行风险）：只经**白名单解析器**（数字、四则、括号、分数、幂、受限函数名）转换后再交给 sympy 求值；输入长度与复杂度设上限，求值设超时；
- 简单四则/分数仍先用标准库 `fractions.Fraction`，sympy 只用于方程与化简，降低依赖面。

### 4.2 校验范围（MVP）
| 题型 | 校验方式 |
|---|---|
| 纯计算（四则、括号、小数、分数、竖式结果） | 让模型在 JSON 里额外给出 `expression` 与 `answer`；服务端用 `Fraction`/受限解析器独立求值并比对 |
| 方程/简易方程 | 解方程（sympy）或代入验算 |
| 应用题 | 要求模型输出「列式」；对列式求值，与其答案比对（只能验证"算对没有"，验证不了"列式对不对"） |
| 几何（面积/周长公式） | 公式代入验算；带图题不校验 |
| 无法形式化（带图、文字推理、开放题） | 标记「未能自动验算」，降低置信、默认提示「建议请老师确认」 |

### 4.3 不一致处理
- **一致** → 正常展示，仍带「AI 可能出错」提示。
- **不一致** → **不向学生展示该答案**；改为「这道题我没有把握，已请老师帮忙」并自动进入求助队列（§5），同时记录一条 `verify_mismatch` 事件供统计。可允许**最多重试 1 次**（换提示词让模型复核），仍不一致才升级——控成本、避免反复。
- **校验器自身解析失败** → 视为「未能验算」，不当作错误也不当作通过。
- 校验结果仅用于**路由决策与教师可见标记**，不向学生宣称「已验证正确」（避免给出虚假确定感）。

## 5. 升级老师机制与教师看板

### 5.1 触发条件
1. AI 返回无法解答/低置信（`confidence` 低于阈值，阈值待 §8 实测定）；
2. 程序化校验不一致（§4.3）；
3. 识别失败/学生反复修改识别文字仍对不上（连续 2 次识别后学生点「还是不对」）；
4. 学生主动点「我看不懂 / 我觉得 AI 错了」；
5. 同一题学生已看过讲解后仍重复求助（≥2 次）；
6. 题目含图形（`hasFigure`）且模型自评不确定。

### 5.2 状态机（`help_requests.state`）
`recognizing → confirming → explaining → answered`；任一步可进 `escalated → resolved_by_teacher`；`cancelled`。

### 5.3 教师看板（沿用轮询看板范式，见 §1）
- **每生清单进度**：行=学生，列=今日清单项，点亮已完成；汇总完成率。
- **求助队列**：按升级时间排序；每项显示学生（昵称/座位号）、题目文字、触发原因、等待时长。
- **点开详情**：看到确认后的题目文字 + AI 对话摘要（识别文字、AI 的单一解法、校验结果、学生的追问）；**没有原图**（已删除），这是刻意的取舍，教师需看学生本人的纸面。
- 教师操作：「已处理」「标记为共性难点」「转为错题本」。
- **只显示「已参加」学生**（§14）；未参加学生不出现在清单进度、求助队列、共性难点中。教师可在看板内切换"参加/未参加"（§14.1）。
- **显示规则（决定 A）**：教师自己的管理页可显示 `users.name`；所有**投屏页面**（大屏看板、绑定二维码展示页、统计投屏）只显示**座号**或统计数字。试点期 `name` 一律录入编号或昵称，**不新增字段**。投屏页做成独立路由（如沿用 `/v1/classroom-board/{sid}` 的模式，`v1_classroom_live_board.py:320`），在服务端渲染层就不输出 name，并有测试断言。
- 轮询间隔建议 5–10 秒；仅教师端页面开启，页面隐藏时暂停。

## 6. 共性难点统计

- 来源：`help_requests`，以 `topic`（AI 标注的知识点，教师可改）+ 题目文字归一化后的指纹分组（去空白/标点、数字保留）。
- 规则（可调，**阈值【未确认】需现场数据**）：同一晚内同一知识点或相同题目被 ≥3 名不同学生求助 → 在看板顶部提示「建议集体讲解：[知识点] 共 N 人求助」。
- 展示：知识点、人数、代表题（匿名，不显示姓名即可点开）、AI 解法摘要，便于教师直接投到大屏讲。
- 一键动作：加入「明日讲评」备忘；可联动讲课屏（`v1_classroom_live_board.py`）作为讲义素材（第二期，不入 MVP）。
- 统计只用已落库的文字，不涉及图片。
- **长期保留的是去标识后的聚合记录**（用户决定 5）：知识点、年级、日期、求助人数、是否升级——**不含学生 ID、晚托班、学校+班级标签、题目原文**。对话日志本身 30 天后清除（§7.3）。去标识在清除任务中完成：先写入聚合行，再清除明细。
- 小样本保护：某知识点当日求助人数 < 3 时，聚合行不对外展示具体日期粒度（并入周粒度），避免从统计反推个人。

## 7. 数据与合规

### 7.1 发给模型的字段清单（白名单）

| 调用 | 发送 | 明确**不**发送 |
|---|---|---|
| 作业通知解析 | 教师粘贴/识别出的通知**文字** | 学生姓名、用户名、ID、机构名；通知中出现的他人姓名/电话先做**脱敏**（见下） |
| 视觉识别 | 单张题目照片 + 固定指令 | 任何学生信息；不传文件名 |
| 文本讲解 | 学生确认后的题目文字、可选年级（数字） | 姓名、学号、班级名、学校名、对话历史中的身份信息 |

- 服务端在「构造 prompt 的唯一函数」里做白名单拼装，并有单元测试断言 prompt 不含 `User.name/username` 等（沿用 `ai_grade_homework` 的"不得根据姓名…推断"做法 :4929 附近，但本功能**更严**：根本不传）。
- **年级（用户决定 4）**：传「三年级」这类文字，用于让解法匹配年级、不得超纲；提示词硬性写明"只使用该年级已学过的方法，不要引入初中及以上概念（如设未知数解方程，在低年级不得使用）"。**除年级外不传任何其他身份信息**（不传晚托班、学校、标签、座号）。年级取自 `users.grade`（`app_v924.py:60`，可空）；为空时不传并让教师补全，【未确认】晚托学生该字段是否已维护。
- 年级属弱标识：单独一个年级在 30 人机构内不足以识别个人，但与题目文字组合仍应视为受控数据，不写入 `AIUsageLog`（现状仅记长度，不记 prompt）。

### 7.2 截图里的他人信息
家长截图可能含家长/老师昵称、头像、手机号、群名。处理：
- 视觉识别指令要求「只抽取作业内容，忽略聊天头像/昵称/手机号」；
- 服务端对识别文本做正则脱敏（手机号、证件号、长数字串）；
- 教师确认页展示识别文字，并提示「如含他人信息请删除」；
- 原图识别后立即删除；`raw_text` 在发布后可清空或仅留作业条目（默认发布后清空，减少留存）。
- 【未确认】是否需要在 UI 上提示教师"转发截图前请家长遮挡无关信息"，由用户定。

### 7.3 日志与留存（用户决定 5）

| 数据 | 留存 |
|---|---|
| 原图 | 0（识别后即删，内存处理，不落盘） |

| 共性难点聚合（去标识） | **长期保留** |
| `homework_notices.raw_text` | 发布后清空（只留结构化条目）；最长不超 7 天 |

## 8. 识别测试方案（20–30 张真实作业照片）

### 8.1 样本构成（目标 30 张，最少 20）
| 类别 | 张数 | 说明 |
|---|---|---|
| 手写清晰（印刷题干） | 4 | 基线 |
| 手写潦草（学生字） | 4 | 难点 |
| 竖式计算 | 4 | 进位/借位标记 |
| 分数（横线分数、带分数） | 4 | 排版识别 |
| 几何（含图形/标注） | 4 | 图形题 |
| 整页多题 | 4 | 验证是否需要"只拍一道" |
| 光线差（阴影、反光、倾斜） | 4 | 鲁棒性 |
| 通知截图（微信长文本，含他人头像昵称） | 2 | 对应 §2/§7.2 |

- **照片来源（用户决定 8）**：机构教师用**真实练习册**拍摄，**只拍题目区域，不出现姓名**（不使用学生手写作答的原件，除非同样不含可识别信息）；**私有存放（不进仓库、不进 CI、不进 PR 附件）**；评测结束后**删除**，评测脚本在输出里只写文件序号，不写路径外的元数据。
- 通知截图样本（2 张）需先由教师遮挡头像/昵称/手机号后再入测。
- 因照片来自练习册而非学生作业，"手写潦草"类难点样本可能不足——可由教师本人手写模拟作答区域，但**结论需注明与真实学生字迹存在差距**。
- 每张配**人工标准答案**（题目文字逐字转录），由两位教师独立转写，不一致处第三人裁决。

### 8.2 指标与算法
- **字符级准确率**：1 − 编辑距离 / 标准文本长度（数字与运算符权重更高）。
- **题意准确**（核心指标）：数字、运算符、单位、分数结构、关键条件**全部正确**才算对（二值）。因为一个数字识错就会得到完全错误的解答，字符率高也可能不合格。
- **可用率**：识别结果经学生"改动≤2处"即可确认的比例。
- **图形题**：单独统计"是否正确提示含图/无法处理"，不要求还原图形。
- 多家模型（DeepSeek 视觉实验型 / Qwen / 智谱）**同图并行**；同时记录耗时、失败率、成本。
- 评测脚本放 `scripts/`（只读离线，不接入产品路径）；图片不入仓库。

### 8.3 通过标准（草案；**用户将审核后另行回复**，在回复前以下数值仅供参考，不作为合入门槛）
| 指标 | MVP 通过线（建议） |
|---|---|
| 清晰手写/印刷 题意准确 | ≥ 90% |
| 竖式、分数 题意准确 | ≥ 80% |
| 潦草手写 | ≥ 65%，且要有可修改界面兜底 |
| 几何带图 | 不要求通过；要求 100% 能识别"含图"并提示老师 |
| 整页多题 | 不通过也可，则 MVP 限定"单题取景" |
| 通知截图 | 作业条目召回 ≥ 90%，他人信息不入库 |
| 平均端到端耗时 | P90 ≤ 15s（识别） |
| 失败/超时率 | ≤ 5% |

若首选模型整体未达线：切换备选；仍不达线则 MVP 降级为"学生手输题目文字 + 文本讲解"，识别作为增强项。

## 9. 成本估算

### 9.1 调用次数（每名学生每晚，假设值）
| 场景 | 调用 | 
|---|---|
| 教师导入通知（全班共用，不按学生算） | 文本解析 1 次/班/天（截图方式再加 1 次视觉） |
| 学生每晚求助 | 假设 2–5 题 | 
| 每题 | 视觉识别 1 + 文本讲解 1 + 可能的复核重试 0–1 → 2–3 次 |
| 不会的追问 | 0–2 次/题（MVP 可不做自由追问，只做"升级老师"） |

→ 每名学生每晚约 **4–15 次**模型调用（学生求助型），上限由限流控制（建议每生每晚 ≤ 10 题 / 20 次）。

### 9.2 成本公式与区间
单价**【未确认】**：DeepSeek 视觉实验型、Qwen、智谱各家当前价格与是否收费均需到官方控制台核对，仓库内无价格数据，故不写具体金额。给出公式：

```
每生每晚成本 = 题数 ×〔 视觉(输入图片token×P_v_in + 输出token×P_v_out)
                      + 讲解(输入≈300–600 token×P_t_in + 输出≈400–900 token×P_t_out) 〕
```
- 量级依据：小学题目文字短，讲解输出数百 token；图片按各家规则折算 token（【未确认】各家折算方式）。
- 建议：用 §8 评测时同步记录真实 token（`AIUsageLog.input_tokens/output_tokens` 已有字段 :461，`_ai_usage_values` 已解析），**以实测数据回填**此表，再给出元/生/晚区间。
- 成本控制手段：限流（§3.5b）（每生/每晚）、校验失败最多重试 1 次、解析失败不自动重试、识别结果学生确认前不调讲解、MVP 不做自由聊天。

4. 设备绑定参数：每生最多设备数（草案 2）、绑定码有效期（草案 10 分钟，远程绑定最长 30 分钟）、设备凭据有效期（草案滚动 180 天）。
5. 学生 `must_change_password` 与设备绑定：沿用 #701 的决定？
6. 限流数值（§3.5b）以压测结果校准，是否同意？
7. 清理机制：惰性清理，还是 Render Cron（部署面变更）？
8. `users.grade` 是否已为晚托学生维护？（决定 4 传年级依赖它。）
9. 备份文件在回滚窗口后保留多久（草案：合并后观察 7 天后删除）？

## 12. 设备绑定登录（业务补充 1）

### 12.1 原则
家长自愿参加、自带平板 → 主登录方式是**一台平板绑定一个学生账号，之后保持登录**。学生不输密码、不输码。日码+座号仅作机构备用平板的备用方式（§12.5）。

### 12.2 绑定流程
1. 教师在"晚托管理 → 学生 → 绑定平板"生成**一次性绑定码**，页面显示**二维码 + 短链接**（二维码里是链接）。管理页（教师自己的设备）可显示学生 `name`（试点期为编号/昵称）；若要**投屏展示二维码**，使用投屏版，只显示**座号**（决定 A）。
2. **家长或教师**用**要绑定的那台平板**扫描：iPad/安卓的系统相机识别二维码 → 提示"用 Safari/浏览器打开" → 打开绑定页。二维码可显示在教师手机/电脑屏上，也可由教师把图片/链接发给家长在家绑定（有效期内）。
3. 绑定页显示"要把这台平板绑定到 [学生显示名] 吗？"并要求点**确认绑定**（POST 才消费令牌；GET 只展示页面，防止链接预览/扫描器误消费）。
4. 服务端原子消费令牌 → 新建设备记录 → 设置设备 Cookie → 跳转学生首页。之后每次打开自动登录。
5. 绑定页在**微信/QQ 等内置浏览器**里检测到时，提示"请点右上角用 Safari/系统浏览器打开"，不继续绑定（否则登录凭据只存在于那个内置浏览器）。

### 12.3 数据与凭据（新表，随 M1）
```
device_bind_tokens
  id, school_id, student_id, token_hash(SHA-256；明文只在二维码里出现一次), created_by, created_at,
  expires_at(默认 10 分钟；远程绑定最长 30 分钟), used_at(nullable), used_device_id(nullable)

student_devices
  id, school_id, student_id, secret_hash(设备凭据的哈希), label(可由教师改，如"小明的华为平板"),
  ua_summary(浏览器/系统/型号摘要，不存完整 UA 指纹), bound_at, bound_by, last_seen_at,
  revoked_at, revoked_by, revoke_reason
```
- 令牌：≥128 位随机数，URL-safe；库里只存哈希；一次性；到期或使用即失效；每生同时最多 1 个有效令牌（新生成使旧的失效）。
- 设备凭据：≥256 位随机数，放**服务端设置的 HttpOnly、Secure、SameSite=Lax Cookie**（不放 localStorage——iOS Safari 对脚本可写存储有长期不使用清理，Cookie 更稳，仍需 §13 实测），库里只存哈希。
- 登录态：设备凭据换取标准学生令牌的做法**沿用 #701 的"不修改现有认证代码、由中间件逐请求校验吊销"模式**（`changying/web/classroom_quick_login.py:589` 起的中间件、`claim_nonce` :132）；设备被解除后，下一次请求即失效。是否复用 `make_token`（`app_v924.py:833`）及其过期时间的具体取值，以实现时读代码为准【未确认】。
- 一台设备同一时刻只绑一个学生；一个学生最多 N 台（草案 2）。

### 12.4 教师端：设备管理
- 学生详情页列出已绑定设备：名称/型号摘要、绑定时间、最后在线、状态。
- **一键解除**（二次确认）：写入 `revoked_at`，该设备下一次请求回到"这台平板已解除，请联系老师重新绑定"页。
- 学生被置为"未参加"时自动解除其全部设备（§14.1）。
- 绑定、解除、令牌生成都写审计日志（沿用既有 `implementation.audit`，如 `classroom_quick_login.py:372` 的用法）。

### 12.5 备用方式：日码 + 座号（沿用 #701，用户决定 3）
- 适用：机构备用平板（不绑定个人）。
- **码按日、按晚托班生成，教师每天打开页面显示**；次日旧码自动失效。这是对 #701 的调整——#701 的码绑定在"课堂 session"（`:310,:315`），晚托没有课堂，需引入"晚托日会话"（新表 `after_school_day_sessions`）；是否改 #701 表或另建并行表，实现 PR 里读代码后定【未确认】，倾向另建，避免改动已上线结构。
- **限流按"班级码会话"计算，不按 IP**（机构共用出口 IP，按 IP 会误伤整班）：同一码会话内连续错误累计，超限锁定该码会话并提示教师。
- **不加 PIN**（用户决定）。已知取舍：座号可被冒用；缓解 = 教师可看座号占用情况、一键重置（复用既有 `/teacher/classroom-sessions/{sid}/join-code/seats/{seat}/release`，:376，和座号对照表 :779 的做法）、审计日志。
- `must_change_password` 学生：#701 默认拒绝（`classroom_quick_login.py:19`）；沿用你对 #701 的决定。

### 12.6 安全与验收清单（P3）
| 项 | 验收 |
|---|---|
| 单次使用 | 同一令牌两个并发消费，只有一个成功（数据库原子更新，测试覆盖） |
| 过期 | 过期令牌被拒；文案不泄露学生信息 |
| 链接预览 | 仅 GET 访问不消费令牌 |
| 哈希存储 | 库中无令牌/设备凭据明文（测试断言） |
| 解除即失效 | 解除后该设备下一请求 401，页面回到说明页 |
| 未参加联动 | 置未参加 → 设备全部解除 |
| 跨租户 | 其他学校教师不能为本校学生生成/解除（403/404） |
| 速率 | 消费端点限流（按令牌与全局，不按 IP 单一维度） |
| 开关 | `AFTER_SCHOOL_DEVICE_BIND` 关闭时端点与页面 404 |
| 日志 | 日志不含令牌、Cookie、key |
- 本项属 AGENTS.md §6 高风险（登录/JWT/权限、新表、环境变量、Cookie），**需单独获批**。

## 14. 参加状态管理与试点前后对比（业务补充 3、4；v3 按决定 B、C 修订）

### 14.1 参加 / 未参加（含同意登记硬前置）
```
club_participation        school_id, student_id(唯一), status(participating|not_participating),
                          seat_no(晚托班座号，唯一于晚托班；投屏页只显示它),
                          consent_received(bool), consent_date(date), consent_registered_by(user),
                          effective_from(date), updated_by, updated_at
                          CHECK(status<>'participating' OR (consent_received AND consent_date IS NOT NULL AND consent_registered_by IS NOT NULL))
club_participation_events  student_id, status, effective_date, actor, created_at   -- 只追加
```
- **硬性前置条件（决定 B）**：未登记同意书不能设为「参加」。三层保证：①唯一的状态变更函数在服务端校验（不通过 409）；②数据库 `CHECK` 约束；③测试覆盖接口、批量、任何导入路径。登记内容只有「是否收到、日期、登记教师」，**不存扫描件**。
- 新学生默认**未参加**。`seat_no` 放在新表而不是 `users`（决定 A：不新增 users 字段）；与 #701 的座号对照关系实现时对齐【未确认：#701 座号是否稳定跨日】。
- **教师看板、清单分配、求助入口、设备绑定码生成都只面向「参加」学生**；未参加学生不出现，也**不采集其任何数据**。
- 置为「未参加」：确认弹窗 → 自动解除设备 → 从看板移除 → 已有历史保留；家长要求撤回并删除时另有「撤回并清除」（§7.4）。已登记的同意书记录在撤回时一并标记失效。
- 管理页：学生列表按状态筛选、批量设置、显示计数；每次变更写 `club_participation_events` 与审计日志。

### 14.2 试点设计：参加学生自身前后对比（决定 C）
- **取消**「教师代记未参加学生」与组间对照：系统里**不存在任何未参加学生的作业/介入数据**。
- 阶段由新表 `pilot_phase`（晚托班、阶段 `baseline|ai_on`、开始日期、设置教师）控制：
  1. **基线期（前 2 周）**：只开作业清单（`AFTER_SCHOOL_ASSISTANT` 开、`AFTER_SCHOOL_AI_HELP` 关），学生勾选完成；教师照常辅导并用"记一次辅导"按钮计数；
  2. **AI 阶段**：教师把晚托班切到 `ai_on`（并由用户开启 `AFTER_SCHOOL_AI_HELP`），此后开放拍照求助。
  - AI 入口开放的条件是 **环境变量开 + 晚托班处于 ai_on** 两者同时满足。
- 指标口径（均针对已参加学生本人）：

| 指标 | 定义 |
|---|---|
| 作业完成率 | 当日已勾选完成条目数 ÷ 应完成条目数（按学生按日；汇总到周） |
| 当晚按时完成率 | 在晚托结束时间前完成的条目 ÷ 应完成条目 |
| 教师介入次数 | AI 升级后教师处理次数 + 教师手动"记一次辅导"次数（`teacher_interventions`：`ai_escalation | manual`；基线期只有 manual） |

### 14.3 对比页（教师/管理员）
- 对每个参加学生：基线期 vs AI 阶段的周均完成率、按时完成率、介入次数；汇总所有参加学生的变化。
- 保护：参加人数 <5 时不显示汇总；导出 CSV 不含学生 ID/姓名，仅汇总；无个人排名。
- 页面固定声明：**无对照组，只是参加学生前后对比**；时间推移、作业难度、新鲜感等都可能影响结果；样本约 30 人，不做显著性结论，**不代表因果效果**。
- 统计不调用 AI，不向任何外部服务发送数据。

### 14.4 显示规则（决定 A）
- 教师自己的页面（管理、进度、对比的个人明细）可显示 `name`；试点期 `name` 一律录入**编号或昵称**，**不新增字段**。
- **所有投屏页面**（大屏看板、二维码展示、统计投屏）只显示**座号**或统计数字；服务端渲染层不输出 name，测试断言响应中不含 name。
- 个人明细曲线只在教师管理页出现，投屏模式只出汇总数字。

## 15. 「家长端说明」所需内容清单（业务补充 5）

说明：这是**内容清单**，不是最终文案；成稿后由用户/机构定稿，随纸质同意书一并发放（D1）。菜单路径因系统版本而异，**写入说明前必须用实机核对并截图**【未确认】。

1. **这是什么、是否自愿**：晚托作业助手做什么、不做什么；自愿参加、可随时退出；退出不影响正常晚托。
2. **数据说明（与同意书一致）**：发送给 AI 的只有题目文字和年级；不发送姓名、学校、班级；拍的照片识别后立即删除；对话记录保留 30 天；去标识的共性统计长期保留；如何撤回并删除。
3. **推荐浏览器**：iPad → **Safari**；安卓 → 系统自带浏览器或 **Chrome**。不要用微信/QQ/夸克/UC 等内置或第三方浏览器打开绑定链接；不要用隐私/无痕模式；不要禁用 Cookie。
4. **绑定步骤（图文，每步配截图）**：
   - 前提：平板联网、系统已更新、电量足；
   - ① 教师给出二维码或链接（也可能在家由教师发给家长）；② 用**这台平板**的相机扫码（或在平板浏览器打开链接）；③ 选择"用 Safari/浏览器打开"；④ 核对屏幕上的学生显示名，点"确认绑定"；⑤ 看到"绑定成功"；⑥（可选）添加到主屏幕。
   - 注意：二维码 10 分钟内有效且只能用一次；过期请联系老师重新生成；不要把二维码/链接转发给他人。
   - 常见问题：扫了没反应；跳进了微信；提示已过期；提示"已绑定其他学生"；换平板或换孩子怎么办（联系老师解除后重绑）；清了浏览器数据怎么办。
5. **锁定平板的设置方法（家长/机构自行操作，系统无法强制）**：
   - iPad：**引导式访问**（设置 → 辅助功能 → 引导式访问；在 Safari 中三击顶部/Home 按钮启动），限制只能停留在 Safari；配合**屏幕使用时间 → 内容和隐私访问限制**，限制 App 安装和网页内容（只允许长缨网址）。
   - 安卓：系统的**屏幕固定/应用固定**（安全或显示相关设置中）；华为的**家长控制/青少年模式**、小米的**儿童空间/家长控制**可限制可用应用与网址。
   - 锁定时必须**保留相机与文件上传**（否则无法拍题），要在实机验证 T11（§13.2）。
   - 如实说明：锁定能减少误用，不是安全保证；系统也无法强制家长锁定。
6. **孩子使用规则**：只拍题目区域；避开人脸、姓名、学号；光线要亮；AI 可能出错，要自己判断，不确定就点"请老师帮忙"。
7. **如何解除绑定/换设备/退出**：联系老师（给出联系渠道）；老师一键解除，约束与时效说明。
8. **故障排查与反馈渠道**：登录不上、拍照没反应、图片太大等；已知问题清单（来自 §13 测试）。
9. **同意书要素**（供纸质件）：参加意愿；监护人签字与日期；数据使用说明；撤回方式；联系人；**回执栏：平板品牌型号、系统及版本、日常使用的浏览器**（用于 §13 矩阵，决定 D）。机构收到后由教师在系统里登记「已收到 / 日期 / 登记教师」（§7.4，不存扫描件）。
10. **需用户决定的内容**：机构联系人与渠道、同意书最终文本、是否在说明里推荐"添加到主屏幕"（取决于 T4 结果）。
